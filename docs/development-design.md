# 家庭成长站开发设计文档

版本：0.4 开发设计  
更新日期：2026 年 10 月 20 日  
对应：[产品设计 0.6](product-design.md)、[Q01 至 Q13 决策](open-questions.md)

本设计覆盖管理员全局访问、普通用户本人访问、确认前可由创建人删除、确认后仅追加更正的事件与反向记录、月底总结与确认、钱包统一入账，以及试卷跳过积分事项。商品兑换独立服务仅保留后续边界，不实现。以下方案已进入实现，实际版本、测试和部署结果见[交付记录](delivery-report.md)。

## 1 技术栈与边界

| 部分 | 建议方案 |
|---|---|
| 语言与运行时 | TypeScript、受支持的 Node.js LTS，实施时固定精确版本 |
| 应用框架 | Next.js App Router，运行在 Node.js，不用 Edge 连接本地 SQLite |
| 页面 | React、Tailwind CSS、shadcn/ui，手机优先、电脑自适应 |
| 数据库与访问 | SQLite、Prisma，版本及本地驱动在实现时一起锁定 |
| 测试 | Vitest 单元／集成测试，Playwright 手机与电脑流程 |
| 部署 | 单应用 Docker 容器、独立 Compose、Nginx HTTPS 入口 |

不再采用早期草案的 Python、Django 和 Gunicorn。不额外建立独立前端服务器、Redis、队列或用户管理后台。Next.js 可以自行 Docker 部署，见[官方部署文档](https://nextjs.org/docs/app/getting-started/deploying)。

代码按四个边界组织：页面与请求解析 → 用例服务 → 纯计算函数／数据库访问 → SQLite。规则函数接收普通 TypeScript 数据，不能依赖 Next.js、Prisma、会话或系统时间；用例服务负责权限、事务及审计。数据库适配集中在窄边界，不建立通用插件平台。

建议目录（尚未创建）：

```text
src/app/                    登录、首页、金钱、积分、事件、结算页面与写请求
src/components/             卡片、表单、历史、待办和基础 UI
src/domain/                 周期、事项匹配、抵销、总结计算
src/services/               事件确认、反向记录、结算与钱包入账
src/server/                 Prisma 接入、会话、权限、项目规则加载
config/agreement/           线下确定后维护的协议和奖惩规则
prisma/                     数据模型与迁移
scripts/                    受控初始化与数据库维护入口
tests/unit/                纯规则测试
tests/integration/         数据库、权限、事务、请求
tests/browser/             手机及电脑业务流程
deploy/                    Docker 与入口运维配置
```

不创建商品、上传、订单、券、家长关系或在线协议发布模块。管理员新增定额记录类型属于第一期。管理员是否叫爸爸或妈妈只影响显示名，角色使用 ADMIN／USER。

## 2 认证与授权

初始两个管理员显示名为爸爸、妈妈，普通用户为 Ellie。数据库维护独立登录名、密码安全哈希、角色和启用状态，不开发用户创建页面。受控初始化通过应用密码哈希边界写入，并保留执行账号和时间；不要在 SQL 或日志里保存明文密码。

复用经核实兼容的认证库提供数据库会话和凭据校验，精确库与版本在工程初始化时选定，不自创 Token 协议。Cookie 使用 Secure、HttpOnly、SameSite；写请求校验来源与 CSRF，不把 Next.js 页面可见性当作后端授权。官方边界说明见 [Next.js 认证文档](https://nextjs.org/docs/app/guides/authentication)。

每个数据读取及写入用例在服务端执行一次对象权限：ADMIN 可访问全部；USER 只能操作 subject_id 等于自己的记录及钱包。操作人只从有效会话取得，客户端不能指定 actor_id 冒充他人。首页待办范围同权限，普通用户看不到他人待确认事项。

事件、反向更正和月度总结采用同一确认规则：创建人为初始已确认人，再合并按时间追加的本人意见；对象本人和任一管理员确认即可。异议覆盖初始确认且优先阻断。月度总结生成即代表发起管理员确认，不要求其他管理员再确认；任一管理员可在本人确认后入账。角色和 ID 取自账号／快照，不以爸爸、妈妈显示名判断。旧快照缺角色时按原参与人合同解释，不覆盖历史数据。登录框关闭自动大写、自动纠错及拼写检查。

## 3 核心数据模型

所有业务金额用整数分、积分用整数，时间戳保存 UTC、页面及周期按 Asia/Shanghai。TypeScript 数值边界检查整数安全范围，不用浮点人民币参与计算。

| 对象 | 主要字段和约束 |
|---|---|
| User | 登录名唯一、显示名、角色、密码哈希、启用状态 |
| RecordType | 类型代码唯一、名称唯一、每次金额（整数分）、每次积分、创建管理员和时间；只新增不覆盖 |
| Session | 认证库管理会话、用户、有效期；不在业务日志暴露会话密钥 |
| AppSettings | 单个家庭设置、协议月初始锚点、设置管理员和时间；只做首次设置入口 |
| Period | 对象、起止、输入修订号、结算状态；对象与起点唯一 |
| Event | 对象、记账周期、实际发生时间、事项、次数、原因、依据、创建人及时间、提交标识 |
| EventConfirmation | 事件、确认账号、意见、时间；每人对同一事实版本不重复确认 |
| Reversal | 作为 Event 的一种类型，关联原事件、反向次数或来源调整、原因；不能无来源制造金额 |
| Settlement | 周期、输入修订号、规则修订及快照、事实快照、哭泣统计、原始／封顶汇总、净变化、状态、入账人和时间 |
| SettlementConfirmation | 总结快照、用户、确认时间；旧快照的确认不移给新结果 |
| Wallet | 对象、资产 MONEY／POINTS、当前余额；对象与资产唯一 |
| WalletEntry | 钱包、来源结算、变化前后余额、变化值、操作人和时间；结算与资产唯一 |
| AuditEvent | 谁、何时、对什么对象、做了什么、必要原因和变更摘要 |

以上为逻辑对象，Reversal 采用 Event 类型及来源引用即可，不要求单独建表。预设协议规则为项目配置；管理员新增的定额类型存于数据库。每次结算同时读取类型对应表并保存完整快照及内容摘要。管理员无需 GuardianChild 关系即可全局访问。

钱包当前余额用于快速读取，流水为核对依据；初始化金额也生成受控流水。正式帐号均从零开始。需要增加余额时通过类型与记录进入月底结算，不提供单独初始余额页面。事件与反向记录在没有其他成员确认过时允许创建人标记删除；确认、结算、流水与审计没有删除入口。确认后错误只能追加反向记录更正。

## 4 首用周期与事件记录

### 4.1 周期

无初始设置时，管理员进入首次设置页选择协议月起点，普通用户看到等待设置。保存初始锚点、设置人及时间。已有设置不能由第二次请求覆盖，同内容重复提交返回已有设置，不同内容报告冲突。

按初始日号逐月计算边界，缺日取当月最后一日，不沿用截短后的日号；例如 1 月 31 日→2 月末→3 月 31 日。周期左闭右开，按北京时间 00:00 分界。所有对象沿用家庭锚点，周期按需创建，无定时任务。

### 4.2 普通事件

输入为对象、事项、发生时间、次数、原因、试卷类型／分数／等级等依据及提交标识。金额、积分、余额、操作人不由客户端输入。默认一次，按事项检查所需依据、来源及每日限制；不同默写不能因同日被误判为重复。

事实不覆盖；确认记录保留历史。未被他人确认的记录可由创建人标记删除并记录审计，所有读取与计量排除删除记录。事件与必要审计在同一事务写入，钱包不变。相同提交标识重复请求返回已有事件；确认不会自动变成入账。家务同对象同日最多一条有效确认，错误通过反向记录抵销，不静默删掉重复数据。

未确认事项在首页和月底页面提示有权的登录人。月底页面完成确认后重算总结，无需通知队列、短信、后台轮询或单独的未解决事项流程。

## 5 规则与总结算法

规则配置包含原协议的等级、分数区间、单次金额、积分、每日限制、月度哭泣奖励及两个金额上限。用户线下讨论后提供新协议，再修改配置和项目部署；不开发规则编辑页面、在线签署、下一周期发布或自动切换任务。

生成总结使用当前部署的协议规则和数据库中的记录类型对应表，快照保存原文、结构化配置及修订标识。规则变化影响尚未入账的总结时需重新核对；旧入账总结始终保留原规则。对旧期反向纠错使用旧期快照，不套新单价。

纯函数建议合同：`calculateSummary(period, events, rules)`，输出有效事项次数、来源、哭泣次数、月度奖励候选、原始金额与积分、封顶后金额、净变化。函数无数据库与当前时间依赖，相同输入结果相同，不修改输入。

计算顺序：

1. 检查周期事实已按流程确认，合并原事项和关联反向记录的有效次数，保留完整链路。
2. 根据成绩或等级匹配事项；按日期检查家务每日上限，保留逐次默写等来源。
3. 汇总各类原始金额与积分，正金额为奖励，负金额绝对值为扣减。
4. 查询本协议月有效学习哭泣次数；零次自动产生 +500 元候选月度奖励，非零不产生。反向纠正哭泣记录后重新计算，而非只查数据库是否存在原始 crying 行。
5. `reward = min(rawReward, 100000)`，`deduction = min(rawDeduction, 100000)`，`moneyDelta = reward - deduction`。
6. `pointsDelta` 独立汇总，包含确认的试卷跳过 -10，不受金额上限约束。
7. 输出可解释总结，不改钱包；家庭核对无漏记后确认。

例：原始奖励 130000 分、扣减 20000 分、积分 +8，净变化为金钱 +80000 分、积分 +8。封顶只在周期汇总应用，不按登记次序分配给事件。无哭泣记录是系统候选依据，不能宣称已证明现实中没有发生；用户可补录后重新核对。

## 6 反向记录与已结算调整

反向记录关联原事件，显示相反方向，写明纠错原因。按原事项抵销，不当成无关新奖励或新扣减；总抵销不能超过原有效次数。原始记录仍可查看，不能用删除或直接将 confirmed 设为 false 代替冲正。

未结算周期：原事件与反向记录抵销后计算，包括金额方向、家务有效次数和哭泣次数。例：错扣一次 -100 元，关联 +100 元抵销后该项有效扣减为零，不占用普通奖励上限。

已结算周期：保留原结算及流水；读取其事实与规则快照，追加纠正，重新计算该周期应结总额，减去原已入账额及已入账的相关调整，得到尚应补回／扣回的差额。差额作为本次结算单独的 priorPeriodAdjustment，不重新占用当前周期的普通奖惩上限，月底统一入账。

例如旧周期扣减原始 1200 元、封顶扣 1000 元，纠正其中 100 元后仍应扣 1000 元，差额为零；不能直接多补 100 元。若原错误哭泣被抵销，还应重新计算旧期 500 元条件及上限，再得实际差额。

来源调整同一份结算只能消费一次，保存已经处理的纠错 ID 与修订。测试覆盖重复冲回、部分冲回、原期和本期封顶、多次调整。该设计只服务用户要求的不可删除纠错，不建设通用财务补偿平台。

## 7 试卷跳过积分事项

第一期记录 skip_extra_paper，一次 -10 积分，按实际跳过日期的自然月最多一次、限家庭课外试卷。本人提出、管理员确认，保存试卷依据、时间及操作人；不是商品订单或可库存权益。

该事件与其他事件同样，日常不直接改钱包，月底汇总后入账。无需库存、发券、领取、自动过期或兑付服务。反向记录纠正错误，历史仍保留；同自然月一次限制按抵销后有效次数检查，未确认的并发申请不能最终确认成两次。

用户已确认只可使用已结算积分且至少 10 分；未结算奖励不可用。登记和最终确认在事务中读取积分钱包，减去尚未入账的有效已确认跳过支出后判断；不提前改钱包，不新增余额预留表。

## 8 结算确认与原子入账

周期到期后页面查询事实并展示待确认事项；确认后生成快照，对象本人及任意一位管理员核对（创建即确认），再由管理员提交入账。无自动入账或规则任务。未确认记录在页面处理，不默默排除后将总结标成完整。

事件增加、反向记录、确认变化或规则变化使原总结修订不再匹配，应保留原确认历史并重新生成总结。仅使用周期输入修订号和规则修订解决这个事实变化问题，不新增全局令牌平台。

短事务内依次：

1. 验证管理员，检查周期到期、总结输入修订与确认齐全；已入账返回原结果。
2. 读取钱包，计算 `moneyAfter = moneyBefore + moneyDelta + moneyAdjustment`，允许负数。
3. 写两种资产流水和余额，关联结算及已消费的旧期调整来源。
4. 标记结算已入账，保存操作人、时间、审计，一起提交。

中途失败全部回滚；每周期唯一入账及每结算资产唯一流水防止并发／重复入账。SQLite 只有一个写事务，不能假定有行锁；入账使用适配层明确的短事务及数据库约束，锁竞争明确返回失败，不自动重试业务多次。实现时针对所锁定 Prisma 版本核验事务 API，不能混用不同大版本接口，见 [Prisma 事务文档](https://www.prisma.io/docs/orm/v7/prisma-client/queries/transactions)和 [SQLite 事务说明](https://sqlite.org/lang_transaction.html)。

## 9 页面与请求边界

服务端组件读取数据，客户端组件处理表单与移动交互。写入统一经 Server Actions 或 Route Handlers 中选定的一种公共入口调用用例服务，不在多个入口复制规则，页面权限仍须在服务层执行。开发时选定入口后固定错误格式及测试。

| 页面或动作 | 行为 |
|---|---|
| 登录／退出 | 凭据验证、会话建立或注销，记录时间 |
| 初次设置 | 仅管理员选择家庭周期锚点，防止重复覆盖 |
| 首页 | 当前对象钱包、待结算、本月事件、可见待办 |
| 金钱／积分 | 钱包与结算流水、本人或管理员全局历史 |
| 记录类型 | 仅管理员新增名称、每次金额和积分；普通用户只读取可选类型 |
| 新增事件 | 事项、时间、次数、原因、依据，无金额输入 |
| 事件确认／异议 | 追加本人意见，不改事实和钱包 |
| 反向记录 | 选择来源、反向数量和原因，保持链路 |
| 跳过试卷 | 新增 -10 积分事项，检查自然月有效次数 |
| 月度总结 | 待确认记录、有效次数、哭泣判定、封顶和钱包预计变化 |
| 总结确认／入账 | 绑定快照确认；管理员最终事务入账 |
| 协议查看 | 展示项目规则及已结算快照，无线上编辑 |

不提供删除、原地修改事实、规则发布、商品、上传或商城接口。表单错误保留输入，事实变动显示重新核对；越权不泄露其他用户数据，失败不显示成功或余额已变更。

页面采用统一设计变量和基础组件，避免默认后台模板：手机 360 至 430 像素首屏清晰，卡片数字大，底部导航，电脑使用多列和表格。加载、空状态、错误、负余额与未确认状态有明确展示。

## 11 Docker 与 Oracle 部署

建议项目目录 `/opt/family-rewards`，独立 Compose。Next.js 使用 Node.js standalone 构建，应用内部端口建议 3000，SQLite 位于宿主受限持久化目录；不把数据库或应用端口直接暴露公网。

Nginx 在网站入口按域名 ellie-rewards.duckdns.org 转发；未匹配域名和直接 IP 默认拒绝。入口及应用使用专用前端网络，不能加入代理内部网络或挂 Docker Socket。部署前决定复用 Nginx 的具体配置，不能把本稿当作已部署。80／443 与当前代理 8443、9443、2443 分开。

应用建议初始内存上限 512 MiB、不预留、不绑 CPU，实际构建和负载验证后调整。非 root、无额外权限、固定镜像与依赖、restart unless-stopped、日志 10m × 3；数据库和配置持久化，备份验证可恢复。构建尽量本地完成后交付，避免线上构建挤占其他服务资源。

用户要求本期先不做自动任务：不创建周期、结算、规则、过期或备份定时器。先提供手动一致性备份及恢复命令，部署及更新前执行；定时备份另行讨论，不把手动备份说成自动保护。

上线顺序：只读检查、保存备份、构建与本地验收、迁移、启动、HTTPS／登录与家庭流程实测、原三个代理回归。之后升级涉及不可逆迁移时，回滚恢复匹配镜像和数据库，不只切换镜像。不得整机重启、重建 OCI 资源或清理其他服务。

## 12 实施顺序

1. 工程和测试基础；核实并锁定 TypeScript 技术依赖。
2. 登录、ADMIN／USER 权限、数据库初始化和首次周期设置。
3. 原协议规则、事件与确认、反向记录及积分跳过事项。
4. 总结查询、哭泣判定、封顶、共同确认、负余额和原子入账。
5. 手机／电脑看板及历史，完整浏览器回归、手动备份恢复。
6. 选定域名的 DNS／证书／Nginx 配置核验，再独立部署 Oracle。

初始余额与积分不足策略只在依赖功能前确定，不把已明确的 Q01 至 Q13 继续标成待决定，也不因剩余细节扩大产品范围。

## 上线增补：类型目录与协议附件

主导航直接进入记录类型；页面从当前规则生成预设说明，并合并数据库自定义类型。协议附件使用 `/api/agreement-file?format=pdf|docx`，认证后读取固定文件，未知格式拒绝，缺失文件返回明确404；PDF在线、Word下载，私有不缓存。原件及离线转换预览放在 `uploads/agreements`，不进Git和镜像，通过只读持久化挂载交付。不提供上传或文件路径选择接口。

## 上线增补：确认完成与记录删除

已确认／已抵销记录不允许再新增DISPUTE，详情隐藏沟通表单，历史原因及操作人时间继续展示。Event新增可空 deletedAt／deletedBy，迁移只增加字段。创建人在其他任何人首次CONFIRM前可删除；事务检查曾确认意见、已入账周期、仍存在的反向记录。对象锁串行化确认和删除，删除／修订／审计一起提交。已删除记录不出现在历史、待办、计价和反向次数中，详情404，确认和更正拒绝，重复删除幂等。删除不改钱包，修订变化使旧总结失效。原件附件保留不修改，当前应用约定显示最新交互规则。
