# 家庭成长站产品设计文档

版本：0.6 产品设计  
更新日期：2026 年 10 月 20 日  
项目：Family Rewards  
访问地址：`https://ellie-rewards.duckdns.org`

家庭成长站面向家庭长期使用，支持管理员与多个普通用户。手机和电脑访问同一网站，金钱与积分分别展示；平时记录奖惩事实，协议月结束后汇总、核对并统一更新钱包。商品商城后续再做，试卷跳过作为第一期的积分事项实现。

本文按用户对 Q01 至 Q13 的决定更新，原决定见[需求决策记录](open-questions.md)，技术方案见[开发设计文档](development-design.md)。域名已选定，不代表已经核验 DNS、申请证书或完成部署；实际实现与验证状态见[交付记录](delivery-report.md)。

## 1 第一期范围

- 登录、退出；初始三个账号，显示名为爸爸、妈妈、Ellie。
- 爸爸和妈妈是两个独立管理员账号，姓名与权限角色分离，不设置父亲／母亲专属权限。
- 普通用户只能查看自己的全部奖惩、确认、结算和钱包记录；管理员能查看和处理全部用户的数据。
- 手机优先的响应式首页、独立金钱和积分菜单、完整历史与操作时间和操作人。
- 事件记录与确认、反向记录更正、协议月总结、月底确认与钱包入账。
- 金钱钱包允许负数，不因余额不足而把扣减清零或跳过。
- 首次使用时管理员选择初始协议月起点，后续周期沿用该锚点计算。
- 试卷跳过纳入第一期：记录一次使用事项和对应的 -10 积分，不建设商城或履约系统。

不做公开注册、用户创建页面、商品维护、图片上传、商城、商品兑换、现金支付、自动入账任务或在线协议规则发布流程。商品兑换以后可能独立成服务，供多个系统共同使用，当前只保留产品边界，不提前开发公共平台。

## 2 用户与权限

| 能力 | 管理员 | 普通用户 |
|---|---|---|
| 查看账目 | 所有用户的全部记录及汇总 | 自己的全部记录，包括未确认和反向记录 |
| 录入事件 | 为任意奖惩对象录入 | 为自己提交 |
| 确认事件 | 查看并确认全部对象记录 | 确认自己记录 |
| 反向更正 | 为任意对象追加反向记录 | 为自己提出更正并参与确认 |
| 试卷跳过 | 为对象登记及确认 | 为自己提出并确认 |
| 月度结算 | 查看全部总结、发起核对和执行入账 | 查看并核对本人总结 |
| 首次周期设置 | 选择初始起点 | 查看设置结果 |
| 账号维护 | 在数据库中维护，不提供页面 | 不开放 |

所有用户必须登录。服务端执行权限判断，不依赖隐藏页面按钮。操作人取自会话，奖惩对象是记录所属用户，两者必须分开保存。管理员不因拥有全局权限而自动取得他人的确认身份。

事件、反向更正及月度总结统一由对象本人和任意一位管理员确认。创建即代表创建人确认，无需重复点击：管理员创建后只需对象本人确认；用户为自己创建后只需任意一位管理员确认，不要求爸爸、妈妈都确认。保留创建、确认的操作人和时间；任何异议仍需提出人解除，不把创建等同于另一方同意。既有记录沿用创建时间计算，不覆盖历史意见或已入账流水。登录帐号框关闭自动大写和自动纠错，保留输入原文。

## 3 页面与导航

第一期底部导航为首页、金钱、积分、记录类型。电脑可使用侧栏；同一套账号和数据，不单独开发原生 App。右上角提供协议、账号和退出入口。管理员可切换对象或查看全局，普通用户没有他人选择入口。

记录类型页面优先展示八种预设及已有自定义类型，包括金额分档、积分、限制与记一笔入口；管理员新增表单位于列表后。我们的约定提供登录后可见的原始协议附件：PDF 在线预览和 Word 原件下载，附件不公开。

| 区域 | 内容 |
|---|---|
| 顶部 | 家庭成长站、当前对象、当前协议月；管理员对象切换 |
| 钱包卡片 | 已结算金钱余额和积分余额；负数清晰展示 |
| 本月概况 | 事项次数、待确认数、明确标为未入账的预计汇总 |

不显示未实现的商品、商城、心愿或图片入口。金额增减同时使用符号和文字，不只依赖颜色。首屏优先显示余额与待办，表单适合触控，失败时保留输入。

### 3.2 金钱与积分菜单

金钱页显示钱包、本月事件和历史结算；事件表单选择事项并填写发生时间、次数、原因及成绩依据，不直接输入奖励金额。积分页显示钱包、积分事项、反向记录和试卷跳过入口。每日记录不立即改变钱包。

事件历史与钱包流水分开：前者说明发生什么及谁确认，后者说明哪次结算改变余额。两者均支持按周期、事项及状态查看，普通用户可以看到自己的完整奖惩历史，不只显示最终汇总。

2026-11-02 钱包资产范围贯穿“金钱事项／积分事项”、“记一笔”和“完整历史”。各钱包只列所属资产的类型；同时改变金额和积分的自定义类型在两边均出现，但列表只显示当前资产增减。0元考试仍属于金钱事项，反向记录继承原事项的资产。从钱包进入新建时选择框仅显示该钱包类型；完整历史筛选、分页和成员切换保留范围。首页全局成长记录和记一笔继续允许全部类型。

## 4 协议规则与维护

原始来源为 `~/Downloads/家庭奖惩协议.docx`。用户最新决定优先于早期草案。奖惩对应表称为规则表，不是人民币与积分互相兑换的汇率。

|---|---|---:|---:|
| 学校成绩 | A+ | +200 元 | 0 |
| 学校成绩 | A | +100 元 | 0 |
| 学校成绩 | B | -100 元 | 0 |
| 学校成绩 | C | -200 元 | 0 |
| 基础卷 | 90 分及以上 | +100 元 | 0 |
| 基础卷 | 80 分及以上、低于 90 分 | 0 | 0 |
| 基础卷 | 低于 80 分 | -100 元 | 0 |
| 拓展卷 | 85 分及以上 | +100 元 | 0 |
| 拓展卷 | 75 分及以上、低于 85 分 | 0 | 0 |
| 拓展卷 | 低于 75 分 | -100 元 | 0 |
| 对长辈大吼大叫 | 依协议确认发生 | -100 元 | 0 |
| 学习相关哭泣 | 依协议确认发生 | -100 元 | 0 |
| 整协议月无学习相关哭泣 | 查询事件后生成结算候选，家庭确认 | +500 元 | 0 |

奖励与扣减各自每协议月封顶 1,000 元；积分不套用金额上限。学习情绪事项保留先听取解释、帮助解决困难的协议约定，系统不自动识别现实中的情绪，只查询已记录事实。

协议及系统预设规则修改在线下讨论；用户再次提供协议后，由维护者修改项目中的规则配置并部署。第一期不做完整协议编辑后台、三方线上发布、自动切换或「下周期生效」机制。管理员可单独新增定额记录类型。规则配置保留修订标识；生成结算使用当前部署的规则并保存快照。已入账结算不随新规则重算；未入账总结受影响时需重新核对。

### 4.1 记录类型与每次记录

管理员可新增记录类型，定义名称、每次对应金钱和积分；日常只选择类型并登记次数、时间、原因，不直接改钱包。类型既可产生金额，也可产生积分，或者同时产生两者。例：类型“补录奖励”每次 +100 元、+2 积分，登记 3 次，月底原始汇总 +300 元、+6 积分，再与其他奖惩共同应用月度上限。

“对长辈大吼大叫”录入时必选对象：爷爷、奶奶、爸爸、妈妈、姑姑、其他。其余类型不显示对象选择；对象保存在记录证据中并于详情展示，不影响金额规则。旧记录没有对象时仍可阅读，不替家庭补填历史对象。

记录类型本期支持新增与查看，不原地删除或覆盖已有类型。新类型不追溯修改旧类型；旧结算保留当时类型及单价快照。已有考试、家务等系统类型继续遵循原协议条件。

## 5 协议月

首次使用由管理员选择协议月初始起点，普通用户不能更改。系统保存锚点，后续按原始日号逐月计算，不在每次月末截短后逐月漂移。缺少对应日时使用该月最后一日 00:00，周期为左闭右开。

例：选择 10 月 18 日，周期为 10 月 18 日 00:00 至 11 月 18 日 00:00。选择 1 月 31 日，后续边界为 2 月末、3 月 31 日。此为同一家庭的初始周期设置，新增用户沿用，不单独建设多协议日历。

时间按北京时间展示，系统保存 UTC 时间戳；发生时间、录入时间、确认时间、入账时间分别保存。周期在查询时按锚点计算，无需定时任务提前生成。已使用起点不允许无痕改动。

## 6 事件与确认

事件保存对象、事项、发生时间、次数、原因、等级或分数等依据、录入人、录入时间及确认信息。默认一次，同一试卷或默写保留来源标识，家务同日不得重复获得积分。

未被其他成员确认的记录允许创建人删除，其他人无此权限；任何其他成员确认过后均不能删除。删除仅标记并保存操作人／时间／审计，从正常列表和结算排除，不物理抹除。存在有效反向记录时先处理反向记录。已确认或已抵销的记录关闭新增沟通入口，历史沟通原因和确认继续在时间线展示；未完成确认时允许沟通和解除。确认不触发钱包更新。

月底页面列出未确认事项并通知当前登录人处理。管理员可处理所有对象的待办，普通用户只看到自己待办；不把其他对象的敏感事项推送给无权查看的人。处理完成后生成最终总结，不悄悄遗漏尚未确认的事项。

## 7 月度汇算与钱包

### 7.1 汇算步骤

协议月结束后，管理员打开月度汇算页面：系统查询全部事项及反向更正 → 列出待确认记录 → 登录人完成确认 → 统计有效次数 → 查询哭泣记录并生成总结 → 奖励和扣减分别封顶 → 家庭核对同一份总结 → 管理员执行入账。

月底无有效学习哭泣记录时，系统自动提出 +500 元月度奖励；有记录则不提出。总结说明查询周期、有效次数和判定依据，家庭确认前只是候选结果，不能当作没有漏记的证明；若发现漏记，先补记录再重新生成。不另建「月度条件认定」独立审批流程。

### 7.2 封顶与余额

封顶作用于整月汇总，不把单条事件拆成部分金额。例如原始奖励 1,300 元、原始扣减 200 元，结算奖励 1,000 元、扣减 200 元，金钱净变化 +800 元。

金钱新余额＝旧余额＋本次结算金钱净变化，允许为负。例如原余额 50 元，本月净变化 -200 元，新余额为 -150 元。积分独立汇总，试卷跳过作为 -10 积分事项参与，不转换为现金。

帐号钱包从 0 元、0 积分开始；不设置余额初始化页面。需要增加金额或积分时，新增相应记录类型并登记事件，月底统一结算。

### 7.3 总结、确认与流水

总结包含对象、周期、规则修订与快照、事件及反向记录、有效次数、原始奖惩、封顶差额、金钱与积分净变化、哭泣查询结果及月度奖励、确认人及时间。

确认后一次性更新两个钱包，保存变化前余额、变化值、变化后余额、结算来源和执行人及时间。相同周期只入账一次；中途失败全部回滚。事件或规则变化使旧总结确认失效，必须重新核对。第一期不配置自动结算、自动转账或自动规则发布任务，页面自动查询不等于后台自动入账。

## 8 反向记录更正

已确认数据不可删除；确认前删除也保留删除标记与审计。原事实、确认与流水始终留痕。录错扣减时增加一条正向补回的反向记录，错误奖励则追加负向抵销记录，关联原记录并注明原因、操作人和时间。

反向记录是纠错，不是新的普通奖励或处罚：在原事项方向抵销，避免错扣补回被当成奖励而再次受奖励上限影响。未结算时汇总原事项与反向次数后计算；不能把同一笔错误重复全额冲回。

原记录已经结算时，旧结算不删除、不重新入账。用原规则与原周期封顶重新计算纠正后的应结净额，和此前已结净额的差额形成待处理的调整记录，在下一次确认结算中入账；调整单列，不占用新周期普通奖惩上限。原始结算和调整链都可追溯。

## 9 试卷跳过

第一期实现积分事项 `跳过一份课外试卷`，单次 -10 积分，自然月最多一次，孩子提出、管理员确认，仅适用于家庭安排的课外试卷。使用日期决定自然月，不按协议月判断。

直接记录本次跳过事实与积分变化，不发放可囤积券，不做申请订单、库存、物流或自动过期任务。该事项确认后纳入本协议月积分汇总，月底统一扣入钱包，和其他事件保持一致。错误通过反向记录处理。

跳过只使用已结算积分，足够 10 分才能登记；本月未结算奖励不可用。可用积分为钱包余额减去尚未入账的已确认跳过支出，反向抵销的支出不重复扣除；登记和确认时均检查，钱包仍只在月底更新。

## 10 后续商品服务

商品名称、图片、金钱或积分价格、兑换历史保留设计；第一期不创建对应页面、接口、数据表和存储。后续可能拆成独立兑换服务供多个系统使用，届时明确钱包归属、认证与结算边界，当前不开发共享权限或跨系统扣款平台。

## 11 技术与部署方向

建议采用 TypeScript 全栈：Next.js、React、Tailwind CSS、shadcn/ui，数据库 SQLite，数据访问层 Prisma。具体依赖与镜像版本实施时核实并锁定。用户界面采用统一视觉设计，手机卡片及大按钮、电脑多列和表格布局。

Docker Compose 独立部署至现有 Oracle Ubuntu ARM64，服务域名为 `ellie-rewards.duckdns.org`。Nginx 依域名转发到家庭应用内部端口，应用端口与数据库不直接公开；80／443 网站入口与现有代理端口分开，部署前核验配置，不改动代理密钥和节点。

配置与数据库持久化、日志轮转、资源限制、备份恢复、固定镜像和非 root 容器作为部署要求。无 OCI 资源重建、整机重启或其他服务清理。本稿不表示已修改 DNS、Nginx 或服务器。
